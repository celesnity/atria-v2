# search.py reference

Run from anywhere with an absolute path; each subcommand prints one JSON
object to stdout (`ensure_ascii`, exit 0 — soft failures return `{"error"}`).

## Backends

`ATRIA_MAP_BACKEND=db` (default) routes through the GeoRAG engine — a
dedicated PostgreSQL container (`map-db`, localhost:5433) with PostGIS
(spatial), pg_trgm (fuzzy), full-text search, and pgvector (OpenAI
`text-embedding-3-small` semantic similarity) fused into one hybrid score.
Output shapes are IDENTICAL to the legacy JSON engine, still on the 0–100
score scale. If the DB is unreachable the CLI silently falls back to the
JSON engine (stderr warning only), so callers never break.
`reverse_geocode` / `find_duplicates` / `explain_match` exist only on the
db backend.

## Normalization (applies to `search` and `geocode` queries)

1. lowercase, collapse whitespace; 2. strip Vietnamese diacritics (đ→d);
3. expand abbreviations longest-n-gram-first from the dataset dictionary
   (q1→quan 1, tp hcm→thanh pho ho chi minh, nvl→nguyen van linh, …).

Dataset keys were pre-folded and pre-expanded the same way at ingest, so
"vincom q1", "Vincom Quận 1" and "vincom quan 1" all match.

## Place awareness (data-derived, no hardcoded places)

City mentions in queries are detected against a **gazetteer derived from the
dataset itself at load/import time** (`scripts/gazetteer.py`): distinct
city/district values from the POI + address rows, plus variants generated by
generic admin-prefix stripping ("tp ho chi minh" → "ho chi minh"), no-space
concatenation ("sai gon" → "saigon"), and alias links mined from the
dataset's abbreviation dictionary (`sg → "sai gon / thanh pho ho chi minh"`
links sg/sai gon/saigon to TP HCM; hcm, tphcm, hn, dn the same way). On the
db backend the derived table is stored as `map_admin_areas` by
`db_import.py`. New cities in future datasets work automatically; exonyms
not present in data can be added via `data/place_aliases.json`
(`{"aliases":[{"name":"<data value>","alias":"..."}]}`).

A detected city is a **HARD filter**: "quán cafe ở saigon" returns only
TP Hồ Chí Minh cafes; if the city has no matches the result is honestly
empty (never places from another city). Districts are detected/stored but
deliberately NOT hard-filtered (district names can double as street names);
district words keep working through the location scoring.

## Subcommands

### `search "<query>" [--limit 8] [--city <name|alias>] [--category <key>]`
Category-aware POI search. Detects a category phrase inside the query
("cafe", "nha thuoc", "tram sac"…) and a city mention (any gazetteer alias:
saigon, sg, tphcm, hanoi, hn, danang, dn…), uses leftover tokens as a
district/name constraint. `--city` accepts the same alias vocabulary
(`--city saigon` works) and overrides the detected city.
Output: `{query, normalized_query, category, city, results: [...], count}`
(`city` = canonical folded form or null); each result: `{poi_id, name,
name_en, category, lat, lng, address, district, city, rating,
opening_hours, score}` (score 0–100, sorted desc).

### `near --lat <f> --lng <f> [--radius-km 3] [--category <key>] [--limit 8]`
Haversine radius search, sorted by distance.
Output adds `distance_km` per result and echoes `origin`/`radius_km`.

### `geocode "<query>"`
Best coordinate match across the address dataset (150 rows) and POIs.
Output: `{match: {kind: "address"|"poi", id, name, lat, lng, full_address},
score, alternates: [up to 3]}`; `match` is null when nothing scores > 20.

### `pois [--city <folded>] [--category <key>]`
Full enriched dump for the dashboard: `{categories, pois, count,
abbreviations}`.

### `categories`
`{categories: {key: {label, label_vi, color, emoji}}, counts: {key: n}}`.
Category keys: cafe, restaurant, hotel, supermarket, convenience, mall,
bank, cinema, hospital, pharmacy, gas, ev_charging, electronics, airport,
bus_station, market, attraction.

### `reverse_geocode --lat <f> --lng <f> [--limit 3]` (db only)
Nearest known POI/address for a coordinate (PostGIS KNN over both tables).
Output: `{origin, match: {kind, id, name, full_address, lat, lng,
distance_m}, alternates, status}`. `status`: `success`; `ambiguous` when
the top two candidates are within 25 m of each other; `not_found` when the
nearest is beyond 2 km (then `match` is null).

### `find_duplicates [--threshold 0.75] [--radius-m 150]` (db only)
Scores POI pairs within the radius for duplication: name trigram 0.45 +
address 0.25 + distance decay 0.20 + same-category 0.10.
Output: `{pairs: [{poi_a, poi_b, score, signals, verdict:
"duplicate"(>=0.90)|"possible"}], count}` sorted by score.

### `explain_match "<query>" --poi-id POIxxx` (db only)
Debug breakdown of how one POI scores under a query: per-signal values
(`lex`/`fts`/`vec`/`trgm`/`legacy`/`loc`), fusion weights, scoring branch,
final score, detected `city`, and `rank_in_results`. A POI excluded by the
hard city filter reports `excluded_by: "city_filter"` with its `poi_city`.

## Quality baseline

`scripts/eval.py` vs the 60 public evaluation queries, both backends:
poi_hit@1 100% (11/11 answerable), category detection 100% (34/34).
City precision (`data/eval_city.json`, 15 queries incl. saigon/sg/tphcm/
hn/dn aliases): 100% on both backends — gated at >= 95%.
Geocode (`eval.py --geocode`): 92% hit@1 on the alias-derived gold set
(misses are ambiguous street-only aliases); handwritten hard set 100% on
db vs 90% on json. Three eval queries target POIs absent from the
participants dataset (coverage gaps). Use `--backend json|db|both` for
side-by-side metrics with latency.
