# data_copilot — conversation-scoped storage + live tables & charts in chat

**Date:** 2026-07-03
**Branch:** `feat/data-copilot-module`
**Status:** Approved design, ready for implementation planning

## Problem

The `modules/data_copilot/` module answers questions over a dataset
(generate → run → repair → verify → report). Three gaps motivate this work:

1. **Wrong storage location.** Ingested datasets and analysis run outputs are
   written into the *module* folder (`<module>/data/`, `<module>/runs/latest`),
   and the audit trail is module-global. Data-processing artifacts should be
   scoped to the **conversation** that produced them.
2. **No live data/chart in chat.** The agent can push a static matplotlib PNG
   (`send_image`) or a module-bound editable grid (`send_editable_table`), but
   it cannot send an arbitrary result DataFrame to chat as a read-only table,
   and the web UI does not render an interactive chart from a spec — even though
   the components to do so already exist, half-wired.
3. **Editable table is module-bound.** `send_editable_table` reads/writes
   `modules/<m>/data/<file>`; once data moves to the conversation folder, its
   save-back must follow.

## Reference audit — `.reference/data-agent`

The module is a deliberate trim of the reference. Node-for-node against the
reference LangGraph pipeline:

- **Ported:** `generate_code → execute_code → repair_code → semantic_verify →
  semantic_fix → generate_report` (the module folds `semantic_fix` into
  regeneration-with-hypotheses).
- **Intentionally excluded (out of scope):** self-evolution DGM engine,
  LangGraph orchestration, Docker executor, FastAPI backend, Next.js frontend.
- **Un-ported pipeline steps (noted, NOT built here):** `generate_plan` (explicit
  analysis-plan step), `human_review`/`classify_review` (HITL plan approval),
  `code_critic` (LLM critique of generated code before execution, distinct from
  the module's static `guardrails`). These are optional quality enhancements
  orthogonal to this work.

## How deep-research "data studio" renders charts (reference for §3–§4)

The agent emits a structured, chart-lib-compatible **chart spec** (`type`,
`title`, inline `data` rows, `dataKeys{x,y}`, `units`, `labels`) as a content
block; the frontend renders it **interactively** (type switcher, edit
fields/colors). Data rides inline because it is capped (~20–50 rows). It is
*not* a PNG. Deep-research uses Recharts; **atria uses chart.js** and already
has the equivalent components.

## Key discovery in atria's web-ui

atria already carries a half-built interactive-chart feature in its native
chart.js stack:

- `data_message` payloads already carry a `suggestions` array
  (`ChartSuggestion`: `chart_type`, `x`, `y[]`, `title`), stored on the message
  as `data_suggestions` (`web-ui/src/stores/chat.ts`).
- `web-ui/src/components/Chat/DataMessage/ChartView.tsx` (chart.js renderer),
  `EditPanel.tsx`, `chartProcessor.ts`, and `web-ui/src/stores/charts.ts`
  (Zustand) all exist — the DataChartBlock equivalent.
- **They are orphaned.** `DataMessage.tsx` renders only a PNG *or* a plain
  table; nothing consumes `data_suggestions` or mounts `ChartView`.

Consequence: "web UI renders a live chart from an agent-provided spec" is mostly
a **wiring job on existing components**, not a Recharts port.

## Decisions (from brainstorming)

- Read-only DataFrame display (not editable) for the new "send DataFrame" path.
- Move to the conversation folder: analyze run dirs, ingested/derived CSVs, and
  the audit trail.
- Rebind `send_editable_table` save-back to conversation-scoped files.
- Live charts render via **native chart.js** (wire up existing components), not
  a Recharts port, not PNG-only.
- Chart `suggestions` are **auto-generated by `analyze`** (agent forwards them).

## Architecture

### §1 Conversation-folder storage

New `modules/data_copilot/scripts/paths.py` — single source of truth for where
artifacts live.

**Keying decision (resolved during planning):** data_copilot's own artifacts are
keyed by **`session_id`** (the 8-char atria session id), not the DB
`conversation_id`. Rationale: the bash-invoked scripts, the agent-side tools, and
the save route must all resolve the *same* directory. `session_id` is available
to all three (env `ATRIA_CONVERSATION_ID`, `cb.session_id`, and the session
record) with no DB round-trip, whereas the DB `conversation_id` used by uploaded
artifacts (`.artifacts/conversations/<conv_id>/`) would require a lookup on every
bash exec. data_copilot's storage does not need to co-locate with uploaded input
files (the agent passes those by absolute path), so a dedicated session-keyed
root is both correct and unambiguous.

- `conversation_root() -> Path`: resolves
  `<ATRIA_WORKSPACE>/.artifacts/data_copilot/<ATRIA_CONVERSATION_ID>/`
  (`ATRIA_WORKSPACE` falls back to `ATRIA_SESSION_DIR`; `ATRIA_CONVERSATION_ID`
  holds the session id). When either env var is unset (bare CLI/TUI with no
  session), fall back to the legacy module dir so the CLI keeps working standalone.
- Helpers: `data_dir()`, `runs_dir()`, `new_run_dir()`, `audit_path()` — all
  under the resolved root.
- Server-side mirror `atria/core/modules/data_copilot_paths.py`:
  `data_copilot_root(session_id, working_dir) -> Path` computes the identical
  path for the tools and the route.

Layout:

```
<workspace>/.artifacts/data_copilot/<session_id>/
    data/         ingested + derived CSVs      (was <module>/data/)
    runs/<run>/   code.py, stdout, figures/*.png, result.csv, result.meta.json
    audit.jsonl   per-session audit             (was module-level)
```

Touch points:
- `ingest.py`: write into `data_dir()`; `resolve_dataset` resolves names against
  `data_dir()`; `list_datasets` lists it.
- `copilot.py`: `_default_out_dir()` → `new_run_dir()`; `audit` reads
  `audit_path()`.
- `audit.py`: append/read `audit_path()`.

### §2 `analyze` emits a result table + chart suggestions

After a verified (or UNVERIFIED) run, `analyze` writes into the run dir:
- `result.csv` — the answer table (the primary result DataFrame). If the
  generated code produced a canonical result frame, persist it; otherwise derive
  a best-effort table from the printed output. (Implementation detail resolved
  during planning — the generated code will be instructed to also write
  `result.csv` to its run cwd.)
- `result.meta.json` — `{columns: [{name, type}], suggestions: [ChartSuggestion]}`.

New chart-detection step (mirrors deep-research's detection): a small
LLM-or-heuristic call over the result columns/dtypes producing 1–3
`suggestions` (`chart_type` ∈ bar/line/area/pie/doughnut/scatter, `x`, `y[]`,
`title`). Keep it cheap and skippable.

`run_analysis` summary JSON gains: `result_table` (absolute path to
`result.csv`, or null) and `suggestions` (list, possibly empty).

### §3 `send_table` tool (read-only)

New handler `send_table_tool.py` + schema in
`atria/core/agents/components/schemas/builtin/web_tools.py`, registered in
`registry.py` and the web tool broadcaster.

- Args: `file` (conversation-scoped CSV path — absolute, or relative to the
  conversation `data_copilot/` root), `title` (required), `suggestions`
  (optional array of ChartSuggestion), `max_rows` (optional, default cap).
- Reads the CSV server-side (reuse the row/column parsing already in
  `store.read_dataset`, generalized to an arbitrary confined path), emits the
  existing `data_message` payload:
  `{title, columns, rows, suggestions, editable: false}`.
- Path safety: resolve and confirm the file is inside the conversation folder
  (or an allowed module path); reject traversal.
- Returns `data_payload` so the bubble re-renders on session reload.

The agent forwards `analyze`'s `result_table` + `suggestions` to `send_table`.

### §4 Wire up the chart.js renderer

In `web-ui/src/components/Chat/DataMessage/DataMessage.tsx`, read-only path:
when `message.data_suggestions?.length`, render a **Chart / Table** view toggle:
- **Chart:** mount `ChartView` driven by the `charts` store
  (`initFromSuggestion(messageId, data_suggestions, data_columns, 0)`), with a
  suggestion switcher and the `EditPanel` (fields + colors + legend), matching
  the existing store API.
- **Table:** the current read-only table.

PNG (`data_image_src`) remains a third view when present. No new dependencies —
chart.js/react-chartjs-2 are already installed.

### §5 Editable table rebound to conversation files

- New route module `atria/web/routes/data_copilot.py`:
  `GET /api/data-copilot/read?session_id=…&file=…` and
  `PUT /api/data-copilot/write` (body `{session_id, file, columns, rows}`) —
  read/write a CSV confined to `data_copilot_root(session_id, working_dir)/data/`
  (reuse the CSV parse/serialize + size/row/col caps from
  `store.read_dataset`/`write_dataset` against this base path). `working_dir` is
  resolved from the session record by `session_id`.
- `send_editable_table_tool.py`: accept a session-scoped file, read via
  `data_copilot_root`, set `source = {session: <session_id>, file: <rel>}`. Keep
  module-bound behavior working when `module` is supplied (back-compat).
- Frontend: `EditableDataTable` / `DataMessage` round-trip `source.session` to
  the new route; keep the `source.module` path for back-compat.

### §6 Charts as PNG + SKILL.md instruction

`send_image` unchanged. Update `modules/data_copilot/SKILL.md` runbook:
- After `analyze`, present the report; then call `send_table` with
  `result_table` + `suggestions` for the interactive table/chart view.
- Optionally call `send_image(path=<figure>, caption=…)` for any matplotlib PNG
  in `figures[]` (now under the conversation run dir, readable by absolute path).
- Update the ingest → review → analyze flow to reflect conversation-scoped
  paths and the editable-table rebind.

## Interfaces / contracts

- `paths.conversation_root() -> Path` (env-driven, module-dir fallback).
- `analyze` summary adds `result_table: str | None`, `suggestions: list[dict]`.
- `send_table(file, title, suggestions?, max_rows?) -> {success, output, data_payload}`.
- `data_message` payload (read-only): `{title, columns, rows, suggestions, editable: false}`.
- `data_copilot_root(session_id: str, working_dir: str) -> Path` (server-side).
- `GET /api/data-copilot/read?session_id=&file=`, `PUT /api/data-copilot/write`.

## Testing

Unit (`uv run pytest`):
- `paths.py`: env-driven resolution + module-dir fallback.
- `ingest`/`resolve_dataset`/`list_datasets`: conversation-scoped.
- `analyze`: writes `result.csv` + `result.meta.json`; summary carries
  `result_table` + `suggestions`; audit at `audit_path()`.
- chart-detection: valid `ChartSuggestion` shapes for representative frames.
- `send_table` handler: payload shape, path confinement, missing-file error.
- conversation data read/write route: happy path, traversal rejection, caps.

Frontend:
- `DataMessage` renders `ChartView` + toggle when `data_suggestions` present.
- `chartProcessor` handling of suggestion → chart config (extend existing test).

End-to-end (real, `OPENAI_API_KEY`, per CLAUDE.md): run the web UI, ingest a
CSV into a conversation, `analyze`, confirm run artifacts land under the
conversation folder, `send_table` renders an interactive chart+table, editing +
Save round-trips through the conversation route.

## Out of scope

Self-evolution / DGM, LangGraph, Docker executor, Recharts, and the un-ported
`generate_plan`/`human_review`/`code_critic` steps.
